# MC1/MC2 verification

Run `res://TESTS/Navigation/MultiCitadelChecks.tscn` with Godot .NET. The runner creates an isolated runtime two-Citadel battlefield with three portals, deterministic authored tie, two destination arms and a shared trunk. No Level001/Level020 terrain, objective placements or waves are saved/changed. One variant forces a mandatory checkpoint; another makes the geometrically nearer destination farther by navigable path. Another retains the real LevelSession/Results pipeline.

Checks: legacy single destination assigns with zero selection A*, ordinary single-Citadel click validation still uses one flood; two independent objective states; three source assignments and authored tie; actual assigned route endpoints; First/Last across destinations; shield preference/status exclusion; build rejection when the wrong Citadel remains reachable; occupancy never reassigns; independent arrival damage; direct handoff and actual DeathReleaseJob child inheritance with checkpoint inheritance disabled; two destinations sharing the same checkpoint produce distinct cached tails; explicit terrain rebuild with no reachable objective refuses spawns without redirecting existing ships; removed-objective movement/score safety; second objective destruction produces exactly one real defeat snapshot/event; 500 enemies reuse initial assignments under the combined route-query budget.

Synthetic measurements: approximately 2.8–4.5 ms for three portal/two-Citadel setup (six neutral selection A* queries); roughly 80–110 ms total to instantiate 500 enemies and manually drain their routes through production two-query budget ticks on this host. Zero new selection queries during those 500 spawns. The post-disable profile pool has two grids (one weighted/default and one neutral), not a pool per objective. These are batch/setup measurements, not frame-time or FPS guarantees. More Citadels, large checkpoint networks, map sizes and supported radii change costs; measure representative authored levels.

MC3 remains open: multiple HP bars/labels, destination-aware F3 visualization, broader authoring UX and desktop F5 visual/playfeel review. F3 retains the primary destination preview until MC3 and must not be used to verify secondary portal routes. The runtime test fixture is not added to Campaign. Headless editor import encounters the host's GodotTools/MSBuild initialization NullReferenceException; standalone SDK build and gameplay test runners work. Standard fixture catalog warnings and deliberately unreachable/disabled-source authoring warnings are expected. Do not claim a whole-suite pass or completed visual verification.

Connected-component regression: the same assigned Citadel has valid approaches on both sides of a proposed disconnection. A mandatory checkpoint on the other side cannot be treated as reachable just because a different approach is reachable. Placement rejects it, and an out-of-band blocker causes source/radius validation to refuse spawn. Component maps are computed once per radius/revision or placement proposal, then shared across sources and live enemies.

Final validation: .NET SDK build passed with zero warnings/errors. MultiCitadelChecks, CheckpointChecks, DeathSpawnChecks, ResultsChecks, PlacementHudChecks, CompactInspectorChecks, StasisTowerChecks and ShieldTargetingChecks passed with no gameplay-runner ERROR lines. In the concurrent eight-runner batch the new fixture measured 6.56 ms setup and 148.9 ms total 500-enemy spawn/drain (host contention), still six initial selection queries and zero per-spawn comparisons. Earlier isolated runs were faster as listed above.
